  SECTION 1: THE SELECTION CRITERION THAT DECIDES EVERYTHING
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Research Gap #1 of this project is "no multimodal fusion in existing
federated learning". To DEMONSTRATE that gap rather than assert it, a
dataset must satisfy two conditions that are easy to confuse.

  CONDITION A — GENUINE PAIRING
    The two modalities must describe the SAME entity at the SAME time,
    and must have been RECORDED that way by the instrument. Pairing two
    independent sources by a rule manufactures a correlation that does
    not exist in the world. If the rule is a function of the label, the
    "fusion gain" measured afterwards is label leakage, not fusion.

  CONDITION B — A SHARED TARGET
    Both modalities must independently carry information about the
    label. Genuine pairing with a target only one modality can predict
    is still a fake fusion task: the second encoder contributes
    nothing, and any apparent gain is noise.

  Worked example of passing A but failing B:
    Genuinely paired cardiac signal + chest image, target = a rhythm
    class read off the signal. The image cannot report a rhythm, so the
    image encoder is decoration and fusion cannot help. The task looks
    multimodal and is not.

  THE TEST THAT SETTLES IT
    Train three models on identical splits: modality A alone, modality
    B alone, and fused. Fusion must beat BOTH unimodal arms by more
    than the seed-to-seed standard deviation. Beating only the weaker
    arm proves nothing — the fused model can reach that by ignoring the
    weak modality entirely.

    Implemented in SIMULATORS/scripts/modality_ablation.py and run as a
    first-class pipeline stage, not as an afterthought.

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

               vital signs database in surgical patients",
               Scientific Data 9:279, 2022.
  Access     : https://vitaldb.net — open, no credentialing required.
               Fetched track-by-track via the public API by
               SIMULATORS/data/loaders/fetch_vitaldb.py (resumable).
  Domain     : Clinical IoMT — intraoperative patient monitoring.
  Licence    : CC BY 3.0. Redistribution of derived arrays permitted

2.1  WHY THIS DATASET

  VitalDB is recorded by Vital Recorder, a single acquisition system
  attached to one patient during one operation. Both modalities come
  out of the SAME operation record. There is no pairing rule anywhere
  in the pipeline — the pairing is a property of the instrument.

  Condition A is satisfied by construction.
  Condition B is satisfied by measurement (Section 5).

2.2  WHAT IS ON DISK

  Windows        : 48,712
  Source cases   : 6,257 surgeries
  Clients        : 9
  Classes        : 2
  Edge servers   : 2

  MODALITY A — intraoperative vital-sign trends
    Shape        : (18, 300)
    Content      : 9 numeric trend channels + 9 observed-masks
    Sampling     : 0.5 Hz over a 10-minute window
    Channels     : non-invasive and invasive pressures, heart rate,
                   temperature and related intraoperative numerics

    WHY 18 CHANNELS FOR 9 SIGNALS
      Operating-theatre monitoring is intermittently observed: a cuff
      pressure appears every few minutes, a probe is detached and
      reattached, a line is flushed. Imputing those gaps and discarding
      the fact that they WERE gaps throws away information, because
      which signals are being watched is itself clinically meaningful —
      an anaesthetist escalates monitoring when a patient deteriorates.
      Each signal therefore carries a parallel binary mask channel
      marking observed vs imputed (GRU-D style). Missingness is treated
      as signal, not as damage to be repaired silently.

    EXCLUDED ON PURPOSE
      The point-sampled high-rate waveforms (ECG_II, PLETH, ART) are
      dropped. At 0.5 Hz a waveform is not downsampled, it is aliased:
      the retained value is one arbitrary instantaneous sample of a
      signal whose information lives at hundreds of hertz. Keeping them
      would add channels that look informative and are not.

  MODALITY B — preoperative clinical and laboratory vector
    Shape        : (34,)
    Content      : demographics, comorbidity indicators, preoperative
                   laboratory values, surgical context
    Provenance   : the same case record as Modality A

    Fields that encode the outcome or its timing are excluded by an
    explicit forbidden-field list (length of ICU stay, in-hospital
    death, admission/discharge and operation timestamps, identifiers).
    A preoperative vector containing a postoperative fact is not a
    predictor, it is the answer.

  LABEL — postoperative ICU admission
    Positive rate: 19.7 % of windows
    Unit         : the label belongs to the OPERATION; every window cut
                   from one operation inherits that operation's outcome.

2.3  LEAKAGE CONTROL — WHY THE SPLIT IS BY CASE

  Windows from one operation are strongly correlated: consecutive
  10-minute windows of the same patient under the same anaesthetic are
  near-duplicates. Splitting windows at random would place near-copies
  of the same operation in both train and test, and the reported score
  would measure memorisation of individual patients rather than
  generalisation to new ones.

  The split is therefore BY CASE, stratified by outcome within each
  surgical type, 70/15/15. No case appears in more than one split.

  Pooled totals: train 34,044 | val 7,308 | test 7,360 windows
  Test cases   : 947 distinct operations

2.4  WHY THE CLIENTS ARE NON-IID BY NATURE

  Clients are surgical operation types (optype), not random shards. A
  thoracic list and a general-surgery list genuinely see different
  patients with different risk. Measured ICU base rate across the nine
  clients spans 3.2 % to 50.7 % — a sixteen-fold spread in the positive
  class.

  This is the honest form of the non-IID condition federated learning
  exists to handle. It is a property of clinical practice, not a
  Dirichlet parameter chosen to make the problem look hard.

  Operation types with too few positive cases to support a local model
  are merged into one combined client, so every client holds at least
  10 positive cases. Without that merge a client can hold a single
  class, its local AUROC is undefined, and any average over clients
  silently drops it.

2.5  SCORING UNIT — WINDOWS TRAIN, CASES COUNT

  The model consumes windows; the clinical question is about the
  operation. Because windows within a case are correlated, window-level
  metrics overstate the effective sample size. Every reported result
  therefore carries BOTH:

    window-level  — what the model optimises
    case-level    — each case's window probabilities averaged into one
                    prediction per operation

  Case-level is the statistically honest and clinically meaningful
  number, and is what should be quoted in the thesis.

2.6  METRICS — WHY AUPRC, NOT ACCURACY

  At a 19.7 % positive rate, roughly 80 % accuracy is free: predict "no
  ICU" for everything. Accuracy is therefore close to uninformative
  here, and AUROC is optimistic under class imbalance. Average
  precision (AUPRC) is the metric that actually moves when the minority
  class is handled well, so checkpoint selection uses AUPRC on this
  dataset and class weighting n/(K·count_k) is applied throughout.

  SECTION 3: DATASET 2 — WEAR (FAST ITERATION)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Source     : Bock et al., "WEAR: An Outdoor Sports Dataset for
               Wearable and Egocentric Activity Recognition",
               Proc. ACM IMWUT, 2024.
  Access     : open download, no credentialing.
  Domain     : Wearable IoT — outdoor activity recognition.

3.1  ROLE OF THIS DATASET

  WEAR is the fast-iteration domain. Its arms train in tens of seconds,
  which makes it the right place to shake out pipeline bugs, verify a
  new flag, or confirm a stage runs end to end before committing GPU
  hours on the clinical data. It is NOT the dataset the multimodal
  claim rests on, for the reason given in Section 5.

3.2  WHAT IS ON DISK

  Windows        : 38,578
  Clients        : 22 (one per subject)
  Classes        : 18 activities
  Edge servers   : 2

  MODALITY A — inertial
    Shape        : (12, 100)
    Content      : 4 body-worn accelerometers x 3 axes
    Sampling     : 50 Hz over a 2-second window

  MODALITY B — egocentric video features
    Shape        : (2048,)
    Content      : two-stream I3D features over the SAME 2 seconds

  PAIRING: hardware-synchronised. The inertial sensors and the head-
  mounted camera are clocked together on one wearer; the two modalities
  describe the same person at the same instant because they were
  captured that way.

  Pooled totals: train 26,424 | val 5,395 | test 5,969 windows

3.3  LEAKAGE CONTROL — TEMPORAL, WITHIN (SUBJECT, ACTIVITY)

  Two properties of this data make naive splitting wrong:

  (a) Windows overlap by 50 %. Adjacent windows literally share one
      second of raw signal. A random split puts that shared second on
      both sides of the boundary.

  (b) A whole-recording temporal split is LABEL-DISJOINT. Subjects
      perform activities in blocks, so cutting each recording at 70 %
      of its duration hands the validation split only the activities
      that happen to fall late in the session — this produced
      validation sets containing 3 or 4 of the 18 classes, making the
      validation score meaningless.

  The split is therefore temporal WITHIN each (subject, activity)
  group, 70/15/15, with a one-window gap dropped at each boundary to
  remove the shared overlapping second. Every split sees every class,
  and no raw sample crosses a boundary.

3.4  A HANDLED DATA DEFECT

  One subject's inertial stream contains 25.8 % missing samples. A
  plain mean/std normalisation propagates a single NaN across every
  window of that subject, and from there into the batch statistics —
  silently destroying a quarter of the input while training continues
  and reports plausible numbers.

  Normalisation is NaN-aware (nanmean/nanstd computed on the training
  split only), and residual NaNs are imputed to the post-normalisation
  mean. Statistics are computed on train only, never on val or test.

  SECTION 5: THE FUSION TEST — MEASURED RESULT
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Protocol: centralised and non-private, so the question is about the
  DATA and is not confounded by federation or privacy noise. All three
  arms share encoder architecture, head depth, optimiser, schedule,
  epochs and seed; only the head input width differs (256 / 576 / 832),
  which is inherent to the comparison. Each arm is RETRAINED on its own
  inputs — feeding zeros to a jointly-trained model measures "what
  happens when a modality breaks", not "what that modality is worth".
  Splits are the dataset's own, so the leakage controls above apply.
  2 seeds.

  VitalDB (7,360 test windows / 947 test cases)
  ─────────────────────────────────────────────────────────────────────
    arm                AUROC       AUPRC    case AUROC   case AUPRC
    signals only      0.8283      0.5281       0.8590       0.6446
    clinical only     0.7700      0.5022       0.7713       0.4961
    FUSED             0.8694      0.6343       0.8875       0.6740

    Gain over the BEST unimodal arm: +0.0411 AUROC, +0.1062 AUPRC
    That is 14.1x the across-arm seed standard deviation.

    Fusion beats BOTH arms, not merely the weaker one.
    → Research Gap #1 is DEMONSTRATED on this dataset.

  WEAR (5,969 test windows)
  ─────────────────────────────────────────────────────────────────────
    arm                AUROC       AUPRC
    inertial only     0.9976      0.9761
    video only        0.9957      0.9629
    FUSED             0.9980      0.9831

    Gain over the BEST unimodal arm: +0.0004 AUROC, +0.0070 AUPRC

    The inertial modality alone already reaches 0.9976 AUROC. There is
    no headroom left for a second modality to fill, so this task CANNOT
    evidence fusion regardless of the sign of the gain.
    → Reported as AT CEILING. It is not counted as a second
      confirmation, and the multimodal claim does not rest on it.

  This asymmetry is stated openly wherever the ablation is reported,
  and the verdict is written into the result JSON by the ablation
  script itself so a downstream reader cannot mistake a ceiling for a
  confirmation. Presenting the WEAR gain as supporting evidence would
  be overclaiming from a saturated benchmark.

  SECTION 6: HOW TO BUILD THEM
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  VitalDB
    python data/loaders/fetch_vitaldb.py          # resumable API fetch
    python data/loaders/preprocess_vitaldb.py     # window + split + partition

  WEAR
    python data/loaders/preprocess_wear.py

  Both preprocessors write, under data/processed/<name>/:
    the modality arrays, labels, meta/case_ids.npy where applicable,
    and the per-client partition indices with partition_meta.json.

  Both clean stale per-device index files before writing. A previous
  run with more clients otherwise leaves orphaned device_NN_*.npy files
  that a later run with fewer clients will happily load.

  VERIFICATION (run before trusting any result)
    python tests/verify_datasets.py --dataset vitaldb
    python tests/verify_datasets.py --dataset wear

  This is an adversarial audit, not a smoke test. It checks split
  disjointness, case/subject leakage across splits, NaN and infinity
  presence, label range, class coverage per split, index bounds,
  partition completeness, normalisation sanity, and agreement between
  partition_meta.json and the arrays actually on disk.

  SECTION 7: PROVENANCE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

  Paths do not identify data. Rebuilding a dataset with different
  window settings leaves every stored path unchanged, so a result file
  that records only "data/processed/wear" cannot be traced to the
  arrays that produced it.

  Every run therefore records a dataset fingerprint (md5 of the label
  array and of partition_meta.json) via engineering/runctx.py.
  Current values:

    vitaldb   labels d3fa814dd4396efd   partition_meta 69feba3f786f9e64
    wear      labels 8aeb2aeeb2bba951   partition_meta 38c58aadc2a84eee

  If a published number cannot be matched to one of these, the data it
  came from is not the data described in this document.
