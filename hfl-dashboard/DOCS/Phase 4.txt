4.3.1  Latency Decomposition Model

  Total round latency:
    L_total = L_sensor + L_preproc + L_inference + L_comm + L_aggregation

  Where:
    L_sensor      ∼ Uniform(2, 10) ms       — sensor sampling jitter
    L_preproc     ∼ Uniform(10, 25) ms      — data normalization / windowing
    L_inference   ∼ Uniform(10, 50) ms      — local model forward pass
    L_aggregation = 15 ms (flat) / 35 ms (hierarchical, 2 hops)
    L_comm        — bandwidth-limited transmission (scenario-dependent)

  Communication latency (dominant term):
    Flat scenarios (device → cloud direct):
      BW = 54 Mbps (WiFi 802.11ax), payload = MODEL_SIZE × NUM_DEVICES
      L_comm = (payload_MB × 8) / 54 ≈ 7407 ms

    Hierarchical scenarios (device → edge → cloud):
      Device→Edge : compressed gradient × 20 devices / 54 Mbps
      Edge→Cloud  : compressed × 3 edges / 1000 Mbps (fiber)
      L_comm ≈ 1700–1760 ms (4.2× faster than flat)

4.3.3  NS-3 Packet Simulation (EVERY scenario, configurable cadence)

  Topology : N IoT nodes ──[WiFi 802.11ax]── Edge AP ──[P2P]── Cloud
             N and the edge count come from the registry, and each edge
             cell gets its OWN wireless channel (see 4.6.1, bug B3).
  Duration : 20.0 simulation seconds per round
  Traffic  : BulkSendApplication carrying the COMPRESSED payload
             (1.49 MB vitaldb / 3.14 MB wear), PacketSink at the cloud
  Monitor  : FlowMonitor → per-flow throughput, packet loss, delay
  Injection: FlowMonitor stats replace analytical estimates where the
             packet-level run executed

  REQUIRES A BUILT NS-3 WITH WORKING PYTHON BINDINGS. Without them the
  script falls back to the analytical path and still prints results
  under an NS-3 heading. See Phase 3, Steps 6-7, and check the
  [OK] / [WARN] line the script prints on startup.

4.3.4  Reliability Model — MEASURED, NOT ASSUMED

  reliability_pct = 100 x (1 - measured_loss_rate)

  where measured_loss_rate comes from NS-3 FlowMonitor:
      loss = 1 - (rx_packets / tx_packets)

  An earlier version computed this from a per-scenario rng.uniform()
  range multiplied by a "consistency factor". That is an assumption
  wearing the clothes of a measurement: the proposed system's range had
  been chosen to sit just above the 99 % target, so the objective could
  not fail, and the figure came out identical on two datasets that
  differ by 2.4x in model size and client count. A number that does not
  move when the system changes is not measuring the system.

  See 4.5.2 for the measured values and 4.6.1 defect B6 for why the
  original topology could not have produced loss at all.

4.4.1  Simulation Architecture

  One CloudSimPlus instance per (scenario, round) combination.
  Single unified datacenter with one large host (avoids multi-DC
  VM placement instability in CloudSim Plus v8.5.6).

  Host configuration:
    PEs         = NUM_DEVICES×2 + (hier ? NUM_EDGES×4 : 0) + 8
    PE MIPS     = 100,000 (max of IoT/Edge/Cloud ratings)
    RAM         = 512 GB | BW = 100 Gbps | Storage = 100 TB
    Power model = PowerModelHostSimple(max=2000W, idle=500W)

4.4.2  VM Configuration

  Layer   | VM count | MIPS    | RAM     | BW
  ─────────────────────────────────────────────────────────────
  IoT     | 20       | 300     | 512 MB  | 10 Mbps
  Edge    | 3 (hier) | 8,000   | 8 GB    | 1 Gbps
  Cloud   | 1        | 100,000 | 64 GB   | 10 Gbps
  ─────────────────────────────────────────────────────────────

4.4.3  Three-Phase FL Scheduling

  Phase 1 — Local Training (IoT VMs, all devices parallel)
    Cloudlet MI : 15,000 (CPU scenarios) / 3,000 (HFL_Proposed, compressed)
    PEs used    : 2 per device
    Submission  : t = 0

  Phase 2 — Edge Aggregation (Edge VMs, hierarchical only)
    Cloudlet MI : 2,000 per edge server
    PEs used    : 4 per edge
    Submission  : delay = trainMI / IOT_MIPS seconds (after Phase 1 finishes)

  Phase 3 — Cloud Aggregation (Cloud VM)
    Cloudlet MI : 500
    PEs used    : 8
    Submission  : delay = Phase1_time + (hier ? Phase2_time : 0)

4.4.4  Analytical Energy Model

  Energy = integrated_power × task_time, computed per layer:

    E_IoT   = [P_idle + (P_max - P_idle) × 0.9] × t_train × N_devices
    E_Edge  = [P_idle + (P_max - P_idle) × 0.7 + GPU_overhead] × t_edge × N_edges
    E_Cloud = [P_idle + (P_max - P_idle) × 0.5] × t_cloud

  Power constants (from hfl_config.json):
    IoT   : idle=1W, max=3W
    Edge  : idle=50W, max=200W  (GPU overhead=30W for HFL_Proposed)
    Cloud : idle=500W, max=2000W

  Note: GPU overhead applies only to EDGE in HFL_Proposed scenario.
  IoT devices are 300-MIPS embedded class (no GPU).

  METHODOLOGICAL NOTE — WHY THESE NUMBERS REPLACED THE EARLIER ONES

  An earlier version of this section reported uplink reduction computed
  as model_size x sparsity, and reliability drawn from per-scenario
  rng.uniform() ranges. Neither was a measurement:

    · the uplink figure restated a compression ratio that had been
      chosen as a constant — a reviewer reproduces it in one division;
    · the reliability figure was the midpoint of a hand-picked interval,
      which is why it came out identical (99.05 %) on two datasets that
      differ by 2.4x in model size and 2.4x in client count. A number
      that does not move when the system changes is not measuring the
      system.

  Both are now measured. Uplink comes from the real compressor; loss and
  delay come from NS-3 FlowMonitor over a real 802.11ax topology.

4.5.1  MEASURED UPLINK  (Objective 1)

  Produced by: python scripts/measure_uplink.py --dataset <ds>
  Method: build the real model from the registry, generate a realistic
  delta, run the REAL GradientCompressor, serialise, count bytes.

  THE FINDING THAT CHANGES THE ACCOUNTING
    Top-k sparsification must transmit an INDEX for every value it
    keeps. Indices are int32 and values are uint8 after quantization, so
    the indices cost four times what the payload costs and dominate the
    wire format:

      indices  80.0 % of transmitted bytes
      values   20.0 %
      headers  negligible

    The nominal "5x sparsity x 4x quantization = 20x" ratio therefore
    overstates full-model compression by more than six times. Measured
    full-model compression is 3.2x, not 20x.

    Under the head-only recipe the frozen encoder deltas are exactly
    zero and send nothing, so measured compression is 13.3x — and that
    gain comes from a design decision (what is trained), not the codec.

  Per-client, per-round (vitaldb: dense update 7.111 MB)
  ─────────────────────────────────────────────────────────────────────
  arm                transmitted     compression   indices   values
  full model            2.250 MB          3.2x     1.799 MB  0.450 MB
  head only             0.534 MB         13.3x     0.427 MB  0.107 MB
  ─────────────────────────────────────────────────────────────────────

  System uplink per round, vs centralized (every client sends dense):

    dataset   centralized   full-model        head-only
    vitaldb      64.00 MB   24.75 MB          5.87 MB
                            (61.3 % less)     (90.8 % less)
    wear        329.47 MB  101.19 MB         12.91 MB
                            (69.3 % less)     (96.1 % less)

  OBJECTIVE 1 (>= 50 % uplink reduction): PASS on both datasets, and it
  passes even in the full-model arm. The head-only recipe is what turns
  a comfortable margin into a large one.

  Artifacts: results/phase5/uplink_measured_<dataset>.json

4.5.2  MEASURED RELIABILITY AND DELAY  (Objective 3b)

  Produced by: python3 ns3/hfl-scenarios/hfl_network_sim.py \
                 --dataset <ds> --rounds 5 --ns3_every 1 --cell_radius 30
  Method: every scenario carries its OWN measured payload through the
  real topology; loss and delay are read from FlowMonitor. No scenario
  uses an assumed loss rate.

  WHY GEOMETRY MATTERS HERE
    All nodes previously defaulted to position (0,0,0). Co-located nodes
    see a perfect channel, every architecture delivers 100 %, and the
    reliability objective becomes a tautology. Devices are now placed on
    a disc of radius r around their access point, so path loss degrades
    SNR with distance and frame errors emerge from the real PHY/MAC.

  vitaldb — cell radius 30 m, n = 5 packet-level rounds per scenario
  ─────────────────────────────────────────────────────────────────────
  Scenario                rx(MB)   delay(ms)      loss(%)   reliability
  CentralizedFL            73.59      24.20   0.274±0.080     99.726 %
  FlatFL_NoDP              73.59      21.27   0.236±0.128     99.764 %
  FlatFL_DP                75.08      23.44   0.226±0.131     99.774 %
  HierarchicalFL_NoDP       5.52      17.90   0.000±0.000    100.000 %
  HFL_Proposed              5.68      17.26   0.000±0.000    100.000 %
  ─────────────────────────────────────────────────────────────────────

  wear — cell radius 30 m, n = 5 packet-level rounds per scenario
  ─────────────────────────────────────────────────────────────────────
  Scenario                rx(MB)   delay(ms)      loss(%)   reliability
  CentralizedFL           284.63      39.21   0.485±0.113     99.515 %
  FlatFL_NoDP             293.01      35.74   0.497±0.079     99.503 %
  FlatFL_DP               287.00      40.44   0.545±0.127     99.455 %
  HierarchicalFL_NoDP      13.58      22.84   0.000±0.000    100.000 %
  HFL_Proposed             13.99      21.66   0.013±0.027     99.987 %
  ─────────────────────────────────────────────────────────────────────

  THE EFFECT REPLICATES, AND SCALES WITH THE PAYLOAD RATIO
    WEAR moves 284 MB in the flat arms against 14 MB in the hierarchical
    arms — roughly 20x, against 13x on vitaldb. The measured loss gap
    widens correspondingly: flat arms lose 0.49-0.55 % here versus
    0.23-0.27 % on vitaldb, while the hierarchical arms stay at or
    within noise of zero on both.

    Two datasets differing in client count (9 vs 22), model size (7.5 vs
    15.7 MB) and task (binary clinical outcome vs 18-class activity)
    produce the same ordering by the same mechanism. That is a
    replication, not a single favourable run — and it is the evidence
    that the earlier hand-picked reliability figure could never have
    provided, since it returned 99.05 % on both regardless.

  READING THIS RESULT HONESTLY
    The hierarchical arms lose nothing (or within noise of it) while the
    flat arms lose 0.23-0.55 %, and the mechanism is not subtle: the
    flat arms push 13-20x more bytes through the same lossy channel, so
    they have 13-20x the exposure. Delay falls correspondingly — 29 %
    lower on vitaldb (17.3 vs 24.2 ms) and 45 % lower on wear (21.7 vs
    39.2 ms).

    All five architectures clear the > 99 % target at this radius. The
    honest claim is therefore NOT "only the proposed system is reliable"
    — it is that the proposed system reaches the target with ZERO
    measured loss and materially lower delay, and that its margin comes
    from transmitting an order of magnitude less data.

  RANGE LIMIT — reported, not hidden
    A radius sweep was run at 30 / 50 / 70 / 90 / 105 / 120 m. Beyond
    ~50 m the link becomes marginal: transfers do not complete inside
    the round window (centralized delivers 31 MB of an expected 73 MB at
    50 m), and by 70 m devices fail to associate at all, giving 100 %
    loss for EVERY architecture.

    Those points are a range limit of the 802.11ax cell, not a
    reliability comparison between architectures, and the loss figures
    there must not be quoted as one. At 50 m the ordering also inverts
    within noise, which is a symptom of truncated transfers rather than
    an architectural effect.

  Artifacts: results/ns3/stress5_<dataset>_r30.csv
             results/ns3/stress_vitaldb_r{30,50,70,90,105,120}.csv

  RELIABILITY IS PER UPDATE, NOT PER RUN.
    The objective concerns a model UPDATE. The whole-run compound
    (per-update raised to the number of rounds) is a different quantity
    and decays fast enough to make a healthy per-update rate look like a
    failure.

    The delay measured above is the communication component of a
    TRAINING round. The < 100 ms objective concerns DEPLOYED inference
    at the edge and is owned by ONNX Runtime in Phase 5. The two must
    never be compared.

  Recorded because the root cause matters more than the fixes: the NS-3
  packet-level code path had NEVER ONCE RUN. NS-3 source was checked out
  but never built, so `import ns` failed, so the script took its
  analytical fallback every time — while still printing results under an
  NS-3 heading. Nothing crashed, so five defects sat undetected in code
  believed to be working.

  Every NS-3 figure produced before 2026-08-04 should be regarded as
  ANALYTICAL, not packet-level.

  B1  DEAD API. The script used `import ns.core`, `import ns.network`.
      That form was removed in NS-3 3.36; the bindings are now flat
      (`from ns import ns`). It raises ImportError even on a correct
      build, which by itself guaranteed the fallback forever.

  B2  MISSING RUNTIME DEPENDENCY. NS-3 >= 3.36 bindings require cppyy,
      which was not installed.

  B3  ONE SHARED WIRELESS CHANNEL ACROSS ALL EDGE CELLS. A single
      YansWifiChannel was created outside the cluster loop, so every
      cell shared one broadcast domain while carrying different /24
      subnets. Distinct SSIDs hide this at the MAC layer, but IP does
      not see SSIDs: GlobalRouter aborted with "Network number
      confusion (192.168.2.2/24, 192.168.1.1/24)". Each cell now has its
      own channel — also the physically honest model, since two edge
      cells are not one radio medium.

  B4  SILENTLY DROPPED DEVICE. Cluster membership used integer division
      (9 devices // 2 edges = 4), so clusters covered devices 0-7 and
      the 9th was never attached to any access point. It contributed no
      traffic, so simulated uplink was short by one client. The last
      cluster now absorbs the remainder.

  B5  CSV HEADER TAKEN FROM THE FIRST ROW. Fieldnames came from
      all_results[0].keys(). Only rounds that ran packet-level carry the
      ns3_* measurements, so whenever an analytical row came first every
      packet-level column was dropped from the output. This is what hid
      the problem: even a successful packet-level run would have written
      a CSV with no packet-level columns. The header is now the union of
      all rows.

  B6  ALL NODES AT THE ORIGIN. Every node defaulted to position (0,0,0),
      so the channel was perfect and loss was structurally zero. This is
      why the earlier implementation needed hand-picked loss ranges at
      all — with no geometry there was nothing to measure.

  LESSON FOR THE THESIS
    A simulator that degrades to an analytical model without failing is
    more dangerous than one that crashes. The startup banner now states
    which mode is active, and Phase 3 Step 7 makes binding verification
    a mandatory environment step.



  4.7  KEY IMPLEMENTATION INSIGHTS
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. Single-DC CloudSim Architecture
   Multi-datacenter simulation in CloudSim Plus v8.5.6 causes
   DatacenterBrokerSimple to misallocate VMs (cloud VM needing 100k MIPS
   placed on IoT DC with 300 MIPS PEs), destroying VMs with pending
   cloudlets. Unified single-DC with one large host is the correct
   academic approach for HFL compute modeling.

2. GPU Overhead Placement
   GPU overhead belongs on EDGE servers (aggregation acceleration),
   not on IoT devices (which are embedded-class, 3W max). Adding 30W
   to IoT devices produced -138% "energy saving" — physically impossible.
   Correct model: IoT saves energy via compressed gradients (5× fewer MI),
   edge incurs minor GPU overhead during brief (0.25s) aggregation.

3. Hierarchical vs. Flat Communication
   4.2× latency reduction from hierarchical communication (1830ms vs 7475ms)
   is consistent with HED-FL (De Rango et al.) findings and validates
   the core premise of our architecture.

4. Reliability Advantage of Proposed HFL
   99.05% update reliability exceeds the 99% QoS target and outperforms
   all baselines including HierarchicalFL_NoDP (98.74%), confirming that
   DP noise does not degrade reliability at ε=1.0.
